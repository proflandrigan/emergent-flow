# Bug Hunt Report: emergent-flow (2026-08-14, follow-up full-codebase sweep)

## Summary

- **Scope reviewed:** Full codebase sweep — `emergentflow/{data, embed, clean, collab, llm,
  eval, server, connections, codegen, ml, stats, timeseries}`, the pytest/CI gates, and the
  reference node catalog. UI (`ui/`) was not re-audited this pass (covered by prior hunt
  reports).
- **Confirmed findings: 9** (1 High, 5 Medium, 2 Low, 1 Info), plus 1 test-infra defect.
- **Overall assessment:** The codebase is in strong shape — the four previous consecutive
  bug-hunt passes have closed out the majority of null-deref/logic defects, and ruff/mypy
  are clean. The remaining confirmed issues cluster in two themes: (1) **silent
  correctness deviations** that degrade an operation to a different, wrong one without
  erroring (SQL OUTER joins compiling to INNER; `ef.embed.text` overwriting a user column;
  the budget-gate "approve" dead end), and (2) **agent-consumption contract violations** in
  the collaboration digest layer (JSON payload truncation producing invalid JSON; the 50KB
  cap being bypassable). Each finding below carries a reproducible demonstration.

## Findings

### High — `"LEFT OUTER"/"RIGHT OUTER"/"FULL OUTER"` join types silently compile to `INNER JOIN`

- **Location:** `emergentflow/data/warehouse/spec_compiler.py`:258-283 (dispatch at 180-210)
- **Class:** Logic error / silent wrong output
- **Confidence:** Confirmed
- **Description:** The join-type dispatch exact-matches the single-word tokens
  `LEFT`/`RIGHT`/`FULL`/`CROSS`/`INNER`. The standard SQL vocabulary `LEFT OUTER`,
  `RIGHT OUTER`, `FULL OUTER` matches none of the special branches (`.upper()` yields e.g.
  `"LEFT OUTER"`) and silently falls through to the INNER default — no `join_type` kwarg and
  no error.
- **Evidence / Reproduction:** Ran `compile_spec` with `type` set to each variant:
  - `LEFT`  → `... LEFT JOIN regions ...`
  - `LEFT OUTER` → `... JOIN regions ...`  ← INNER!
  - `RIGHT OUTER` / `FULL OUTER` → `... JOIN regions ...` ← INNER!
  - `RIGHT` → `... RIGHT JOIN ...`; `FULL` → `... FULL JOIN ...`; `INNER` → `... JOIN ...`; `CROSS` → `... CROSS JOIN ...`
- **Impact:** A user who requests an outer join gets an inner join. Rows from the left/right
  table with no match are silently dropped (and their aggregate contributions lost) — a
  silent data-corruption result. The `query_builder` join param docstring imposes no
  constraint on `type`, and `tests/test_warehouse_spec_compiler.py` only tests the bare
  single-word forms, so `OUTER` variants are unexercised.
- **Remediation:** Normalize the token before dispatch: strip an `OUTER` suffix (e.g.
  `join_type = spec.split()[0].upper()` after validating against a known set), or validate
  `type` against `{"LEFT","RIGHT","FULL","INNER","CROSS"}` and raise `SpecValidationError`
  for anything else, including the `OUTER` forms.

### Medium — `ef.embed.text` silently overwrites an existing `output_column` (data loss)

- **Location:** `emergentflow/embed/__init__.py`:164-191
- **Class:** Data loss / missing guard
- **Confidence:** Confirmed
- **Description:** The API and local paths both do `result[output_column] = ...` with no
  collision check. The docstring promises "_data_ with _output_column_ **appended**", and
  every sibling feature-transform operation in the codebase guards against overwrite
  (`timeseries._check_new_columns`, `ml.reduce_dimensions`, `stats.correct_pvalues`,
  `clean.detect_outliers`, `clean.derive_column`). `ef.embed.text` is the sole exception.
- **Evidence / Reproduction:**
  ```python
  df = pd.DataFrame({'text': ['a','b'], 'notes': ['keep-me','keep-me']})
  text(df, 'text', provider='openai', model='m', client=FakeClient(), output_column='notes')
  # notes column now contains [[0.1,0.2],[0.3,0.4]] — the user's real data is gone
  ```
  Observed: `out['notes'] == [[0.1, 0.2], [0.3, 0.4]]`, no warning/error.
- **Impact:** Silent, irreversible loss of an existing column whenever a user reuses a column
  name. Contradicts the documented append contract.
- **Remediation:** Before assigning, raise (mirror `timeseries`) when `output_column` already
  exists and differs from `column`:
  ```python
  if output_column in data.columns and output_column != column:
      raise EmbedError(f"output_column {output_column!r} already exists; choose a different name")
  ```

### Medium — CLI `run` cannot execute graphs containing effectful (`requires_client`) nodes

- **Location:** `emergentflow/cli.py`:254 (and 243-259)
- **Class:** API/contract misuse / missing client injection
- **Confidence:** Confirmed
- **Description:** `cli.py run` calls `execute(graph, params=params)` with no `clients`/`client`.
  For a graph containing any LLM/warehouse/http node, `clients.for_kind(kind)` resolves to
  `None` and the node raises `MissingClientError`. ADR 0017 explicitly states the CLI "must
  check `requires_client` and pass a client itself," and the server does — the CLI does not.
- **Evidence / Reproduction:** Code reading only (running the CLI would require a graph file),
  but the path is direct: `Clients.from_legacy_client(None)` → `Clients(llm=None, ...)`;
  `execute` threads `None` as `client=`; `ef.llm.call`/`ef.embed.text` raise
  `MissingClientError` on `client is None` (verified at `emergentflow/llm/__init__.py:93-94`
  and `embed/__init__.py:170-175`). The CLI provides no flag to inject a client.
- **Impact:** `emergentflow run <graph-with-llm-node>.json` always fails; the documented CLI
  entry point is unusable for any effectful graph.
- **Remediation:** Have the CLI build a client bundle (as `inspect_graph` does with
  `Clients(llm=GatewayClient(), warehouse=_get_warehouse_client())`) and pass it to
  `execute(graph, clients=...)`, or detect `requires_client` nodes before running and fail
  fast with a clear message rather than `MissingClientError`.

### Medium — Budget-gate "Close this gate to approve execution" is a dead end

- **Location:** `emergentflow/server/service.py`:1054-1069 and `emergentflow/collab/budget_gate.py`:62-91
- **Class:** Logic/control flow — a documented action cannot complete
- **Confidence:** Confirmed (by full-path code reading)
- **Description:** `execute_session` re-runs `check_budget_and_open_gate` on *every* call.
  The budget gate's description and docs say "Close this gate to approve execution," but
  `close_gate` only flips that one gate's status to CLOSED — it never triggers or authorizes
  a run. The next `execute_session` against the still-over-budget graph re-computes the same
  estimate and auto-opens a **fresh** EXECUTE gate, returning `{budget_exceeded: True}`
  again. The run can never actually be approved/executed unless the ceiling is raised.
- **Evidence / Reproduction:** Trace: (a) `execute_session` → `estimate_run_cost` >
  `get_budget_ceiling()` → `open_gate` + returns budget block; (b) `close_gate(gate_id)` →
  status CLOSED (session.py:684-687), nothing else; (c) `execute_session` again → same
  estimate, opens new gate, returns budget block, no execution. Loop forever.
- **Impact:** The gate-approval feature is non-functional for over-budget runs: an operator
  who closes the gate expecting execution is never granted it, and gets no signal that their
  approval was inert. Budget runs are effectively un-runnable via the documented flow.
- **Remediation:** Make closing a budget EXECUTE gate actually advance the run (e.g. when a
  budget gate is resolved CLOSED, re-invoke the execute it was guarding / record approval so
  `execute_session` proceeds once), or, if approval-by-ceiling is the only intended path,
  correct the gate copy and behavior to say execution will resume when the ceiling allows it.

### Medium — `digest_payload` JSON truncation changes `value` type to an invalid-JSON string prefix

- **Location:** `emergentflow/collab/digest.py`:62-72
- **Class:** Type/coercion inconsistency + serialization
- **Confidence:** Confirmed
- **Description:** For a small `kind=="json"` payload, `value` is returned as the original
  JSON object (dict). For a large one, `value` becomes a string that is a raw byte prefix of
  the compact JSON — usually cut mid-token, so it is **not valid JSON** and not the same type
  as the small case. Any consumer that parses `value` for `kind=="json"` breaks depending on
  payload size.
- **Evidence / Reproduction:**
  ```python
  digest_payload({'kind':'json','value':{'k':'short'}}) -> value is dict, truncated not set
  digest_payload({'kind':'json','value':{'k':'x'*1200}}) -> value is str '{"k":"xxxx...' (invalid JSON)
  json.loads(dl['value']) -> JSONDecodeError: Unterminated string at line 1 col 6
  ```
- **Impact:** Agent-consumption path (MCP `get_results`) hands an LLM a truncated, unparseable
  JSON prefix for large JSON results; results that happen to fit are valid. Size-dependent,
  inconsistent output.
- **Remediation:** Keep a stable shape: on truncation either return the original dict unchanged
  plus `truncated:True`/`original_bytes`, or truncate to a valid JSON document (e.g. tokenize
  then re-serialize), never an arbitrary byte prefix.

### Medium — `digest_results` 50KB hard cap is bypassed by a single oversized scalar/text payload

- **Location:** `emergentflow/collab/digest.py`:105-138
- **Class:** Boundary / resource-bound enforcement
- **Confidence:** Confirmed
- **Description:** The cap (`digest_payload` returning `scalar`/`text` verbatim; cap only
  checked *before* digesting each payload) means one huge scalar (e.g. a 1MB string) passes
  through untouched and drives `total_bytes` to ~1MB, violating the documented "50KB hard
  cap on total digest size."
- **Evidence / Reproduction:**
  ```python
  digest_results({'n1':{'out':{'kind':'scalar','value':'A'*1_000_000}}})
  len(json.dumps(result)) == 1000048   # ~1MB, not ≤50KB
  ```
- **Impact:** The LLM-agent digest can silently exceed its bound, defeating the load-protection
  the cap exists for.
- **Remediation:** Enforce the cap per-payload too: give scalar/text an explicit size check and
  a truncation marker (`{"kind":"truncated", ...}`) when a single payload exceeds the remaining
  budget, so no single payload can exceed `MAX_DIGEST_BYTES`.

### Medium — Two catalog personas (`data_modeller`, `experimenter`) have no activation slash command

- **Location:** `emergentflow/collab/chat_runner.py`:106-110 (with persona_defs.py:7-92)
- **Class:** Feature inconsistency / silent no-op
- **Confidence:** Confirmed
- **Description:** `persona_defs.py` registers five built-in personas, and `get_personas`
  surfaces all five, but `_PERSONA_SLASH_COMMANDS` only maps `/data-scientist`, `/researcher`,
  `/ml-engineer`. `/data-modeller` and `/experimenter` have identity files on disk
  (`agents/data-modeller.md`, `agents/emergent-flow-experimenter.md`) yet cannot be activated:
  `_detect_persona_command` returns `None` for them, so the raw text is sent to the CLI as an
  ordinary message and `active_persona` is never set — a silent no-op.
- **Impact:** Two advertised personas are unreachable via the documented activation mechanism;
  a user typing `/data-modeller ...` gets no persona and their slash command leaks into the
  prompt as literal text.
- **Remediation:** Add the two missing entries to `_PERSONA_SLASH_COMMANDS`:
  `"/data-modeller": "data-modeller.md"` and `"/experimenter": "emergent-flow-experimenter.md"`.

### Low — Connection CRUD returns 422 instead of 404 for unknown resources

- **Location:** `emergentflow/server/app.py` `_safe_json` (259-265) + `service.py`
  `delete_connection`/`test_connection_route`/`get_connection_schema` (`:1401-1522`)
- **Class:** Wrong HTTP status code / API contract
- **Confidence:** Confirmed (by code trace; would need a live server to curl)
- **Description:** Deleting/schema-testing a nonexistent profile raises `UnknownConnectionError`
  (a `ValueError`), caught by `_safe_json`'s generic `except Exception -> 422`. Other resource
  stores (flows, runs) return 404 on missing resources. Inconsistent.
- **Impact:** Clients can't distinguish "profile not found" (404) from "bad request" (422);
  deletes against a stale/typo'd name read as a bad request.
- **Remediation:** Map `UnknownConnectionError` to 404 (a specific handler before the generic
  catch), as the flows/runs stores do.

### Info — Reference node module `test_proportions.py` collides with pytest discovery

- **Location:** `emergentflow/nodes/examples/test_proportions.py`
- **Class:** Test-infrastructure defect (filename matches pytest `test_*.py`)
- **Confidence:** Confirmed
- **Description:** This is a reference *node definition* module, but its filename begins with
  `test_`, so pytest auto-discovers it as a test module. Its module-level
  `from emergentflow.stats import test_proportions` imports a function matching `test_*`,
  which pytest collects as a test that requests a nonexistent `df` fixture.
- **Evidence / Reproduction:**
  `uv run pytest emergentflow/nodes/examples/test_proportions.py`
  → `ERROR emergentflow/nodes/examples/test_proportions.py::test_proportions — fixture 'df' not found`.
- **Impact:** Every full `uv run pytest` run reports a spurious ERROR from this node module
  (it aborts that module's collection), polluting CI output. The suite otherwise
  collects/executes.
- **Remediation:** Rename the module to the `_node`-suffixed convention used by sibling
  reference nodes (e.g. `proportions.py`), or add `emergentflow/nodes/examples/` to a pytest
  `norecursedirs`/`collect_ignore` so node modules are never collected as tests.

## Notes & unverified leads

- **`execute_session` drops request-body `params`** (`service.py:1067`): the session-execute
  route forwards only run scopes to `execute_graph`, ignoring any `params` in the body. This
  is likely intentional (the session graph is the source of truth) but is inconsistent with
  `/execute`. Unconfirmed as a bug; would need a client expectation to confirm intent.
- **`eval.label` row_id dtype mismatch** (`eval/label.py:79`): originally suspected to
  silently produce all-NaN labels when `row_id` dtypes differ. **Refuted** — pandas raises a
  `ValueError` ("trying to merge on int64 and object columns") rather than silently
  mis-merging; the failure is loud, not silent. The error message pointing the user to
  `pd.concat` is poor advice but not a correctness bug.
- **Gateway unguarded derefs** (`llm/gateway.py:99-101,191`): `response.choices[0]`.
  message.content, `item["embedding"]` assume populated LiteLLM responses. Plausible but
  could not be reproduced with the real client and the `MissingClientError`/typed-error
  contract is not obviously violated on a valid request; left unproven.
- **Connection profile CRUD TOCTOU** (`service.py:1443-1488`): read-modify-write on the
  shared TOML with no cross-request lock; probabilistic, not deterministically reproducible.
- **`byte_scan_cap` skipped on `dry_run`** (`data/warehouse/adapter_client.py:84-91`,
  replay.py:267-282): asymmetry that may be intentional (a dry run doesn't bill). Needs
  product intent to confirm as a bug.
