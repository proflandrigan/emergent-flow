## Findings

### [MEDIUM] — `reference_time=NaT` silently produces all-NaN weights and a corrupted (all-zero) interaction matrix
- **Location:** `emergentflow/recommend/transforms.py:136-140`
- **Class:** Missing input validation / NaN propagation
- **Confidence:** Confirmed
- **Description:** The NaT guard added for the PR (`transforms.py:129-135`: `if timestamps.isna().any(): raise InvalidRecommenderParamsError(...)`) checks only the `timestamp_col` values. It never validates the `reference_time` argument. `pd.to_datetime(pd.NaT)` returns `NaT` without raising, so when a caller passes `reference_time=pd.NaT` (or a float `nan`, or any NaT-valued value) `computed_reference` is `NaT`. Every `age_days = (NaT - timestamps)` entry becomes `NaN`, and `np.exp2(-NaN/half_life)` yields `NaN` for every weight. The function returns a frame whose `weight` column is all `NaN` **without raising** — the same silent-corruption bug class the PR's own report claims was fixed, but the fix is incomplete because it omits the `reference_time` parameter.
- **Evidence / Reproduction:**
  ```python
  import pandas as pd
  from emergentflow.recommend import weight_interactions_by_recency, prepare_interactions

  df = pd.DataFrame({
      "user_id": [1, 1, 1],
      "item_id": ["a", "b", "c"],
      "timestamp": pd.to_datetime(["2026-01-01", "2026-01-02", "2026-01-03"]),
  })
  r = weight_interactions_by_recency(
      df, timestamp_col="timestamp", user_col="user_id",
      item_col="item_id", reference_time=pd.NaT,
  )
  # r["weight"] == [nan, nan, nan]  (no exception raised)
  im = prepare_interactions(r, user_col="user_id", item_col="item_id", value_col="weight")
  # im.n_interactions == 3, im.density == 1.0, yet im.matrix.toarray() == [[0,0,0]]
  ```
  The CSR constructor at `emergentflow/recommend/interactions.py:117` coerces the `NaN` values to `0` on construction, so the matrix is all-zero while *reporting* `n_interactions=3` and `density=1.0`. A downstream recommender fit trains on an all-zero implicit matrix that claims to be dense — silent garbage, and for algorithms that divide by row/column totals, NaN or zero-division.
- **Impact:** Any SDK user passing an NaT `reference_time` through `ef.recommend.weight_interactions_by_recency` gets silent data destruction instead of a typed error. Unlike the timestamp-column case, this path is **not** covered by the PR's test (`test_null_timestamp_raises_typed_error` only sets `df.loc[0,"timestamp"]=pd.NaT`). Note the visual node does not expose `reference_time`, so this is reachable via the public Python API only — lowering likelihood vs. the column case.
- **Remediation:** Extend the existing guard to cover `reference_time`. After the column-NaT check:
  ```python
  computed_reference = (
      pd.to_datetime(reference_time) if reference_time is not None else timestamps.max()
  )
  if pd.isna(computed_reference):
      raise InvalidRecommenderParamsError(
          f"reference_time {reference_time!r} could not be parsed to a timestamp."
      )
  ```
  Add a test mirroring `test_null_timestamp_raises_typed_error` but passing `reference_time=pd.NaT` and asserting `InvalidRecommenderParamsError`.

### [INFO] — `_auc_at_k` computes an incorrect pairwise AUC on recommendation lists containing a repeated item
- **Location:** `emergentflow/recommend/metrics.py:88-109`
- **Class:** Logic / edge-case (latent, currently unreachable)
- **Confidence:** Confirmed (as a latent formula defect; not reachable through shipped recommenders today)
- **Description:** `_auc_at_k` builds `relevant_in_topk` / `nonrelevant_in_topk` as lists (duplicates preserved) and scores each pair using `topk.index(rel_item)` / `topk.index(nonrel_item)`, which resolve every occurrence to the **first** position. Its denominator is `len(relevant_in_topk) * len(nonrelevant_in_topk)` (also counting duplicates). When the same item value appears at more than one rank, the per-pair rank is wrong and the result diverges from the true pairwise ranking AUC.
- **Evidence / Reproduction:** `_auc_at_k([1, 2, 1], {1}, 3)` returns `1.0`, but the correct pairwise AUC is `0.5`: relevant at ranks 0 and 2, non-relevant at rank 1 → pair (rel@0, nonrel@1) scores 1, pair (rel@2, nonrel@1) scores 0 → `(1+0)/2 = 0.5`. The implementation resolves both `1` occurrences to rank 0 and scores `2/2 = 1.0`.
- **Impact:** None today. I audited every catalog `recommend_fn` (popularity, content, collaborative, NCF, two-tower, GRU4Rec): all iterate `np.argsort(...)` over unique item indices and emit at most one row per item per user, so `evaluate → recommend()` never supplies a duplicate list. The defect is latent; it would only surface if a future recommender (or a caller supplying a custom non-catalog recommender through `recommend`) emitted duplicate item ids in a single user's top-k.
- **Remediation:** If/when duplicate-bearing lists become possible, compute AUC over *distinct* items (or use each item's last/mean rank consistently) with a denominator of distinct relevant × distinct non-relevant pairs. For now, no code change is required, but the brittleness of `.index()` on a list with duplicates is worth a comment or a defensive dedupe.

## Notes & unverified leads
- **GRU4Rec global determinism on GPU (unverified):** `catalog.py` (`_fit_gru4rec`, `_fit_two_tower_impl`) call `torch.use_deterministic_algorithms(True)`. On CUDA, some embedding/GRU ops are not deterministic and PyTorch raises `RuntimeError` at runtime. This mirrors the pre-existing two-tower behavior, so it is not introduced by this PR, and I could not reproduce on a GPU here. Listed for awareness only.
- **`build_sequences` NaT ordering (design choice, not confirmed bug):** when `timestamp_col` contains NaT, `sort_values(kind="stable")` silently places NaT-timestamped events last in each sequence, whereas the sibling `weight_interactions_by_recency` rejects NaT. Ordering is stable and deterministic; the inconsistency is a UX/validation smell, not a demonstrable wrong result.
- **`_fit_gru4rec` batch filter `len(s) > 1` is dead code:** `min_seq_len >= 2` guarantees every sequence has length ≥ 2, so the filter never fires. Harmless.
- **`evaluate` docstring drift:** the docstring (recommend/__init__.py:399) still says "the four per-user metrics" now that precision/recall/ndcg/hit/map/mrr/auc are per-user columns. Cosmetic; the new metrics are documented in the `EvalResult` docstring. Not reported as a finding.
