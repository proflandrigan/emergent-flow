# Bug Hunt Report: PR #147 — experiment-validity static analysis (Epic 17, issue #125)

## Summary
- Scope reviewed: the full PR diff on `feature/experiment-validity-125` against `origin/main` — the new `emergentflow/validity/` package (contract, registry, runner, traversal, artifact, and all 10 rules in `leakage.py`/`temporal.py`/`skew.py`/`metrics.py`), the `ef.validate`/`apply_suppressions`/`enforce_validation_gate` integration, the CLI `validate` subcommand, the `GET /validity-rules` server route, the UI (ProblemsPanel, suppression store, validityRules lookup), and the contract artifacts. Not reviewed in depth: `docs/experiment-validity-rules.md` prose and `epics/epic-17-*.md` (content, not code).
- Confirmed findings: 1 High, 3 Medium, 1 Low.
- Baseline: full suite green on this branch (`3580 passed, 87 skipped` in ~3 min), so every finding below is a behavior not covered by the existing tests. All findings reproduced with minimal local fixtures built from the IR models (no real data, no network).

Overall assessment: the pack is well-structured and the plumbing (registry, runner, artifact, suppression, gate) is sound, but the two **error-severity** rules are built on *topological node reachability*, which is not the property their own rationales claim to be "decidable without inference". Because `enforce_validation_gate` raises on any error-severity diagnostic, the resulting false positives hard-block `compile_to_code`/`execute` on graphs that contain no actual leak — directly violating the PR's stated principle that "a false positive that blocks a run destroys trust in the whole pack." The remaining findings are false negatives (missed leaks) and one misleading message.

## Findings

### HIGH — `target_derived_feature` (severity `error`) false-positives on node reachability and hard-blocks valid graphs
- **Location:** `emergentflow/validity/rules/leakage.py:209-213` (the `reaches(graph, node.id, supervised_id)` gate), rule at `leakage.py:166-228`
- **Class:** Logic error / false positive on a blocking rule
- **Confidence:** Confirmed
- **Description:** The rule fires whenever a `clean.derive_column` node (a) references the target column name in any expression AND (b) can topologically *reach* a supervised node. It never checks whether the derived (target-referencing) **column** actually reaches the model's feature set. A user who derives a feature from the target and then explicitly drops it (or excludes it via the model's `features` param) still trips the rule — and because the rule is `severity="error"`, the shared `enforce_validation_gate` raises `GraphValidationError` from both `compile_to_code` and `execute`.
- **Evidence / Reproduction:** Graph `test.source -> clean.derive_column(columns=[{name:"leaky", expr:"churn * 2"}]) -> clean.select_columns(columns=["age"], drop=["leaky"]) -> ml.fit_estimator(target="churn")`. The derived `leaky` column is dropped from the frame before the model sees it, so no target information reaches the model — yet `run_validity_checks` returns `["target_derived_feature"]`, and `ef.validate(...).ok is False`. `ef.execute(graph)` raises `GraphValidationError ... [target_derived_feature]`, and `ef.compile_to_code(graph)` raises the same. The rule's own rationale documents "the derived column is computed for reporting and never feeds the supervised node" as a false-positive shape it claims not to hit — but node-level reachability cannot distinguish that shape. (The `ml.fit_estimator.features` param would also exclude it; the rule never reads it.)
- **Impact:** Legitimate, leak-free graphs are hard-blocked from compiling/executing with no in-SDK bypass (only manual `apply_suppressions`). This is precisely the failure mode the PR description says error severity must avoid.
- **Remediation:** Do not give this rule `error` severity until it reasons about the derived column reaching the model (read the supervised node's `features` param, or follow `clean.select_columns`/`drop`). Concretely, in `TargetDerivedFeature.check`, before appending a finding, resolve the derive node's output column name(s) (`spec["name"]`) and skip when the supervised node's `features` param is set and excludes every target-referencing derived column. If column-level lineage is out of scope for this story, downgrade the rule to `severity="warning"` (and update the artifact/tests) so it informs without blocking — the same conservative choice every other leak rule already makes.

### MEDIUM — `global_imputation_before_split` misses the node's default strategy (`None` → `"mean"`)
- **Location:** `emergentflow/validity/rules/leakage.py:308-310` (`if strategy not in DATA_DERIVED_IMPUTE_STRATEGIES: continue`)
- **Class:** False negative / unhandled default value
- **Confidence:** Confirmed
- **Description:** The rule only fires when the `strategy` param is explicitly one of `{"mean","median","most_frequent"}`. But `clean.impute_missing` executes with a runtime default of `"mean"` when the param is absent (`emergentflow/nodes/examples/impute.py:76`: `strategy = values.get("strategy", "mean") or "mean"`). A `clean.impute_missing` node upstream of a split with no `strategy` param imputes on the full frame (a genuine leak) yet produces **no** `global_imputation_before_split` finding.
- **Evidence / Reproduction:** Graph `clean.impute_missing(no params) -> ml.train_test_split` returns no findings from `run_validity_checks`. The same graph with an explicit `strategy="mean"` param returns `["global_imputation_before_split"]`. The only difference is IR param presence; execution behavior is identical.
- **Impact:** The leak-detection pack stays silent on the most common configuration (strategy left at its default), so the default-mean imputation-before-split leak goes unflagged.
- **Remediation:** Treat a missing/`None` strategy as the node's default: `strategy = _node_params(node).get("strategy") or "mean"` before the `DATA_DERIVED_IMPUTE_STRATEGIES` membership test. Better, centralize the default by reading it from the node's `ParamSpec.default` so it stays correct if the node's default changes.

### MEDIUM — `target_derived_feature` omits `ml.cross_validate` and `ml.grid_search` (inconsistent with `skew.py`)
- **Location:** `emergentflow/validity/rules/leakage.py:47-55` (`SUPERVISED_TARGET_NODES`)
- **Class:** False negative / inconsistent node-type sets
- **Confidence:** Confirmed
- **Description:** `SUPERVISED_TARGET_NODES` lists `ml.fit_estimator`, `ml.train_classifier`, `ml.train_regressor`, `ml.train_random_forest`, `ml.pipeline` — but not `ml.cross_validate` or `ml.grid_search`, both of which fit supervised estimators on a declared `target` column (confirmed in `cross_validate.py:72` and `grid_search.py:83`). Meanwhile `skew.py`'s `TRAINING_NODES` (line 37-47) *does* include both. A `clean.derive_column` referencing the target that feeds a cross-validation or grid-search node is a genuine target leak the rule misses.
- **Evidence / Reproduction:** Graph `clean.derive_column(columns=[{name:"derived", expr:"churn * 2"}]) -> ml.cross_validate(estimator="RandomForestClassifier", target="churn")` returns no findings. Replacing `ml.cross_validate` with `ml.fit_estimator(target="churn")` returns `["target_derived_feature"]`.
- **Impact:** Target-leak detection gap for the cross-validation / hyperparameter-search workflows those two nodes model.
- **Remediation:** Add `"ml.cross_validate"` and `"ml.grid_search"` to `SUPERVISED_TARGET_NODES`. `_target_column` already returns `None` when the `target` param is absent, so the addition is safe (it can only add findings when a target is actually declared).

### MEDIUM — `fit_before_split` (severity `error`) flags stateless feature generation before a split
- **Location:** `emergentflow/validity/rules/leakage.py:35-44` (`FITTING_TRANSFORMS` includes `transform.generate_features`) + rule at `leakage.py:119-163`
- **Class:** False positive on a blocking rule / rule contradicts its own rationale
- **Confidence:** Confirmed
- **Description:** `transform.generate_features` routes to `ml.fit_transform` with `PolynomialFeatures` (`generate_features.py`). PolynomialFeatures' fitted parameters (`n_features_in_`, `n_output_features_`, `feature_names_in_`) are derived from the column count/names, not from row values or the target — no held-out information is encoded by fitting it before the split. Yet the rule fires an **error** on `generate_features -> train_test_split`, which the shared gate converts into a `GraphValidationError` blocking compile and execute. The rule's own rationale defines the leak as "the fitted parameters therefore encode test information" — which does not hold for a stateless feature generator.
- **Evidence / Reproduction:** For `transform.generate_features -> ml.train_test_split`, `run_validity_checks` returns `["fit_before_split"]` (severity `error`), identical to the genuinely-leaking `transform.scale_features`/`encode_categorical`/`discretize` cases. `ef.execute`/`ef.compile_to_code` raise `GraphValidationError` on the graph.
- **Impact:** A legitimate and common feature-engineering-before-split pattern (polynomial/interaction features computed on the full frame, then split) is hard-blocked from running.
- **Remediation:** Split the fitting-transform set by whether the transform learns data-derived parameters: remove `transform.generate_features` from `FITTING_TRANSFORMS` (keep it in a stateless set the rule does not treat as a leak), or key the rule off the resolved estimator's sklearn type. If the conservative grouping is intentional, the rule must be downgraded to `warning` — the "decidable without inference ⇒ error" criterion is not met while a stateless transform trips it.

### LOW — `train_serve_skew` misreports a transform-count mismatch as an order difference
- **Location:** `emergentflow/validity/rules/skew.py:196-223` (the `if not missing and not extra:` "different order" branch)
- **Class:** Misleading message / set-vs-multiset comparison
- **Confidence:** Confirmed
- **Description:** `missing`/`extra` are computed by *set* membership on transform type, so a difference in the *count* of a transform type goes unnoticed and falls through to the "same transforms, different order" branch. When the training path applies `transform.scale_features` twice and the scoring path once, the rule reports "applies the same transforms ... but in a different order: scoring ['transform.scale_features'] vs training ['transform.scale_features', 'transform.scale_features']" — the actual defect is a missing application, not an ordering difference.
- **Evidence / Reproduction:** Graph `test.source -> sa(scale) -> sb(scale) -> fit` and `test.source -> sc(scale) -> predict`, with `load_model -> predict.model`. `run_validity_checks` emits one finding whose message says the two paths apply the same transforms "in a different order" with chains `['transform.scale_features']` vs `['transform.scale_features', 'transform.scale_features']`.
- **Impact:** The skew is still flagged (so no false negative), but the guidance is wrong and would send a user hunting for an ordering problem that does not exist.
- **Remediation:** Before the order branch, compare type *multisets* (`Counter(t.type ...)`); only report "same transforms, different order" when the multisets are equal (i.e. only a permutation differs), and otherwise emit the accurate missing/extra findings — including when the same type appears a different number of times.

## Notes & unverified leads
- **Warning-severity "any node anywhere" approximations** — `window_crosses_split`, `random_split_on_temporal_graph`, `ranking_metrics_on_random_split`, and `global_aggregate_before_split` all trigger on the mere presence of a split node plus an unrelated feature/aggregate node anywhere in the graph (different branch, different dataset). These are explicitly documented as approximations in the rule rationales and are `warning`-severity, so they never block. Treated as intended, not bugs.
- **`fit_before_split` includes `ml.pipeline`** (`FITTING_TRANSFORMS:39`) even though a pipeline's output is a `Model`, which can never feed a split's `frame` in a type-correct graph. Harmless in practice (no finding in well-formed graphs), but conceptually the set mixes frame-transforms with model-fitting nodes.
- **UI suppression is global across flows** — `ui/src/store/suppressionStore.ts` persists under a single `ef-suppressions` localStorage key, not per flow. A suppression `(rule_id, node_id)` therefore also hides the same finding in any *other* flow that happens to reuse the same node id. Node ids are typically random, so collisions are unlikely; flagging as a fragility, not a confirmed bug.
- **`_referenced_columns` collects every `ast.Name`** (`leakage.py:72-84`), so a math/function name in an expression (e.g. `exp`, `log`) is treated as a column reference. A target column literally named like such a name would false-positive — effectively impossible in practice, not reported as a finding.
- **`enforce_validation_gate` behavior change** — validity `error` findings now make previously-runnable graphs (any fitting transform upstream of a split, or a target-referencing derive feeding a model) fail `compile_to_code`/`execute`. The two error rules' false-positive cases above (Findings 1 and 4) make this gate unsafe as shipped; with those corrected, the blocking behavior is consistent with the PR's stated design.
- **`TrainServeSkew` does not compare transform *params*** — two `transform.scale_features` nodes with different scalers (StandardScaler vs RobustScaler) on the two paths are treated as equal. Acknowledged type-level approximation; noted for completeness.

## Coverage & limitations
- Reviewed the Python pack, gate integration, CLI, server route, UI store/panel, and generated artifacts; did not deep-review the markdown docs prose.
- All repros were built from minimal IR fixtures mirroring the repo's own test helpers; no real datasets, no network, no server round-trip.
- The `-m equivalence` gate and full suite were run green on this branch, so no existing test encodes any of these behaviors.
- Deeper column-level lineage (tracking derived columns through `select_columns`/`features` into the model) is the structural fix for Findings 1 and 4 but is explicitly out of scope for this story ("topological approximations ship first"); the immediate safe fix is severing the two rules' severity from `error` until that lands.

## Fixes applied (this session)
All five confirmed findings were fixed on the branch, verified by the new regression tests and the full suite (3586 passed, 87 skipped — +6 tests vs. baseline):

- **Finding 1 (HIGH):** `target_derived_feature` downgraded `error` → `warning` (it is a topological approximation, not "decidable without inference"), and gained a guard that stays silent when the supervised node's `features` param excludes the target-referencing derived column. `ef.validate(...).ok` is now `True` and `enforce_validation_gate` no longer raises on the reproduced non-leaky graph (`derive -> select_columns(drop) -> fit`). The residual `select_columns`-drop shape is now a warning, not a blocker — matching the pack's stated "false positives must never block" principle. `PACK_VERSION` bumped to 2; both `schema/validity-rules.json` and `ui/src/generated/validity_rules.json` regenerated; docs updated.
- **Finding 2 (MEDIUM):** `GlobalImputationBeforeSplit` now treats an absent `strategy` as the node's runtime default `"mean"`, so the default-configuration imputation leak is flagged.
- **Finding 3 (MEDIUM):** `ml.cross_validate` and `ml.grid_search` added to `SUPERVISED_TARGET_NODES`, closing the target-leak detection gap (consistent with `skew.py`'s `TRAINING_NODES`).
- **Finding 4 (MEDIUM):** `transform.generate_features` removed from `FITTING_TRANSFORMS` (PolynomialFeatures learns no data-derived parameters), so `fit_before_split` no longer error-blocks a stateless feature-engineering-before-split pattern; docs updated.
- **Finding 5 (LOW):** `TrainServeSkew` now compares type *multisets* (`Counter`) before falling through, so a transform-count difference is reported as missing/extra transforms instead of a misleading "applied in a different order".

New regression tests: `test_global_imputation_before_split_trips_for_default_strategy`, `test_target_derived_feature_silent_when_features_param_excludes_derived`, `test_target_derived_feature_trips_for_cross_validate_and_grid_search`, `test_target_derived_feature_is_warning_not_blocking`, `test_fit_before_split_silent_for_generate_features`, `test_train_serve_skew_reports_count_mismatch_not_order` (in `tests/test_validity_rules.py`).
