# Experiment-Validity Rules: `ef.validate` as an Experiment Linter

`ef.validate(graph)` traditionally answers *"do these ports fit together?"* —
type compatibility, cardinality, and param contracts. The experiment-validity
rule pack (Epic 17) makes it answer a harder question: **"is this experiment
valid?"** — target leakage, temporal leakage, train/serve skew, and metric
misuse. Every one of these is a property of the **graph's topology**, which means
the IR can decide it and a linter over generated Python fundamentally cannot.

This page is the rule catalog: each rule's id, rationale, decidability class,
known false-positive shape, and how to suppress it.

> **Not model diagnostics.** This is deliberately a different concept from
> `emergentflow.stats.diagnostics` / `stats.diagnostic_model` / `diagnostic_frame`
> (VIF, normality, heteroscedasticity, autocorrelation — *model* diagnostics over
> fitted results). The experiment-validity rules inspect **shape, not results**:
> they never look at data, a fitted model, or a p-value. They only look at the IR
> topology. `ef.stats` / `research.quality.py` judge statistical validity of
> results; `research.assert_data` checks data values (nulls, ranges, drift). This
> epic inspects neither.

## What rides on the existing channel

Findings are plain `Diagnostic`s on the same `Diagnostics` result `ef.validate`
already returns. Each validity finding adds two fields (both additive and
defaulted, so older consumers that ignore them still parse):

- `rule_id` — the machine-readable rule id (this page's ids).
- `related_node_ids` — the *other* node implicated by a relationship finding
  ("`scale_features` fits upstream of `train_test_split`" names two nodes; the
  primary one is `node_id`, the split is in `related_node_ids`).

`source` is `"validator"`, identical to every other `ef.validate` finding, so the
canvas renders validity findings with zero new plumbing (ADR 0012).

## The rule-pack artifact

The rule metadata ships as **data**, not code, so the canvas can explain a rule
without a Python round-trip and third parties can add rules without forking the
validator:

- `schema/validity-rules.json` — the committed rule pack (`pack_version` +
  per-rule `{id, severity, confidence, title, rationale}`), regenerated by
  `uv run python -c "from emergentflow.validity.artifact import write_validity_rules_artifact; write_validity_rules_artifact('schema/validity-rules.json')"`.
- `ui/src/generated/validity_rules.json` — the byte-identical artifact the
  canvas build consumes, regenerated by `uv run python scripts/export_ui_contracts.py`.
- `GET /validity-rules` — the server serves the same artifact (single source of
  truth via `emergentflow.server.service.get_validity_rules`).

This is **distinct** from `schema/rules.json`, which is the *type-compatibility*
artifact (semantics/subtypes/types). Two different rules artifacts; never
overwrite `rules.json` with the validity pack.

## Decidability classes and severity

Each rule declares a `confidence` (`high`/`medium`/`low`) and is either:

- **decidable-without-inference** — provable from the IR alone (which nodes
  reach which, which ports feed which). Only these may be `error`, because a
  false positive that blocks a run destroys trust in the whole pack.
- **topological approximation** — provable with a stated assumption about what
  the edges mean (e.g. "a transform upstream of a split fits on the held-out
  rows"). These are `warning`.

Warnings never block: `compile_to_code`/`execute` raise only on error-severity
findings via `enforce_validation_gate`. Errors are findings the topology makes
certain.

## The rules

### Leakage (Story 3)

- **`fit_before_split`** — *error / high / decidable-without-inference.* A
  fitting transform (`ml.fit_transform`, `ml.pipeline`, `transform.scale_features`,
  `transform.encode_categorical`, `transform.discretize`,
  `transform.generate_features`) reachable **upstream of** a split node
  (`ml.train_test_split` or `recommend.temporal_split`) fits its parameters on
  the full frame, including the rows the split later holds out. **False-positive
  shape:** a fitting transform on a reporting/EDA branch that never feeds the
  split's frame input. `ml.transform` (apply a fitted transformer) is
  deliberately excluded — applying a fitted transform is the legitimate pattern.

- **`target_derived_feature`** — *error / high / decidable-without-inference.* A
  `clean.derive_column` whose expression references a column that is the
  `target` of a downstream supervised node (`ml.fit_estimator`, `ml.train_*`,
  `ml.pipeline`). The derived feature is a function of the answer, so a model
  trained on it leaks the target. Column references are extracted statically via
  the same AST walk `emergentflow/clean/expressions.py` validates. **False-positive
  shape:** the derived column is computed for reporting and never feeds the
  supervised node, or the name coincidentally matches an unrelated column.

- **`global_aggregate_before_split`** — *warning / medium /
  topological-approximation.* `stats.group_by_aggregate` computed upstream of a
  split aggregates statistics over the held-out rows too. **False-positive
  shape:** the aggregate feeds a reporting/EDA branch, or a summary that never
  enters the model's features.

- **`global_imputation_before_split`** — *warning / medium /
  topological-approximation.* `clean.impute_missing` with a data-derived
  strategy (`mean`/`median`/`most_frequent`) computed upstream of a split fits
  imputation statistics on the held-out rows. `constant` strategy is not a leak
  and is not flagged. **False-positive shape:** imputation that only runs on the
  train branch.

### Temporal (Story 4)

- **`window_crosses_split`** — *warning / medium / topological-approximation.* A
  windowed feature transform (`timeseries.lag_features`, `timeseries.rolling_aggregate`,
  `timeseries.ewma`, `timeseries.time_weighted_aggregate`) upstream of a split
  computes each row's window over neighbors that include the held-out rows.
  **False-positive shape:** the window feeds a reporting/EDA branch, or the
  graph splits a non-temporal frame that merely passes through a window node.

- **`random_split_on_temporal_graph`** — *warning / medium /
  topological-approximation.* `ml.train_test_split` shuffles its rows (it has no
  `shuffle` param; sklearn's default is `shuffle=True`). When the graph contains
  temporal-signal nodes (`timeseries.*` or `recommend.temporal_split`), a random
  split can put future rows in train. Use `recommend.temporal_split` instead.
  **False-positive shape:** timeseries nodes present for EDA while the model
  branch splits an unrelated static frame.

### Train/serve skew (Story 5)

- **`train_serve_skew`** — *warning / medium / topological-approximation.* A
  model served via `ml.load_model` -> `ml.predict` must receive data transformed
  exactly as the data it was trained on. The rule diffs the feature-transform
  chain feeding the scoring `predict`'s frame against the chain feeding the
  supervised training node's frame (when both derive from a common fork), and
  flags transforms present in one but not the other, or applied in a different
  order. **False-positive shape:** the scoring path deliberately serves an
  un-transformed baseline, or the two paths consume different data sources (no
  common fork — the rule stays silent).

### Metric appropriateness (Story 6)

- **`ranking_metrics_on_random_split`** — *warning / medium /
  topological-approximation.* `recommend.evaluate` computes ranking metrics
  (precision@k, recall@k, NDCG@k, MAP@k) against its `test_interactions`. When
  that input is held out by a random `ml.train_test_split` rather than a
  temporal `recommend.temporal_split`, the metric overstates quality on
  time-ordered interaction data. **False-positive shape:** the graph
  legitimately evaluates a non-temporal baseline.

- **`task_mismatched_scoring`** — *warning / medium / decidable-without-inference.*
  `ml.cross_validate` pairs a known classification scoring string (`accuracy`,
  `precision`, `recall`, `f1`, `roc_auc`, ...) with a regression estimator, or a
  known regression scoring string (`r2`, `mae`, `mse`, ...) with a classifier.
  The estimator's task comes from the catalog
  (`emergentflow.ml.registry.get_estimator_spec`). **False-positive shape:**
  unknown estimator keys and unlisted/custom scoring strings are ignored — the
  rule only fires on known catalog tasks vs. known scoring families.

- **`eda_peek_on_test`** — *warning / medium / topological-approximation.*
  `stats.auto_eda` / `stats.eda_profile` whose `frame` input is on a split's
  `test` branch lets the analyst see the held-out distribution before
  evaluation — a form of peeking. **False-positive shape:** the EDA is
  explicitly for reporting after the experiment, or the frame is the train/full
  frame (rule stays silent).

## Suppressing a finding

A finding is suppressed **per rule + node**, and the suppression lives *beside*
the graph, never on it (same discipline ADR 0019 articulates for provenance —
`emergentflow/collab/lineage.py`). `ef.validate` itself stays pure: it always
returns every finding.

`ef.apply_suppressions(diagnostics, suppressions)` is the pure filter the
canvas and CLI call at their boundary:

```python
import emergentflow as ef

result = ef.validate(graph)
filtered = ef.apply_suppressions(result, [["fit_before_split", "n-scale"]])
```

`suppressions` is a JSON-native list of `[rule_id, node_id]` pairs. A diagnostic
is dropped when both its `rule_id` and `node_id` match a pair; non-validity
diagnostics (no `rule_id`) are never suppressed. The canvas stores these pairs
per flow as workspace state; the CLI reads them from a file (see `emergentflow
validate --strict`).

## Dogfood gate

Zero findings on all bundled example graphs is a regression-tested requirement
(`tests/test_validity_dogfood.py`): where a demo genuinely trips a rule, the demo
is fixed rather than suppressed. This is the epic's own dogfood gate — the pack
must not be a source of noise on the project's own pipelines.

## Regenerating the artifacts

```bash
uv run python -c "from emergentflow.validity.artifact import write_validity_rules_artifact; write_validity_rules_artifact('schema/validity-rules.json')"
uv run python scripts/export_ui_contracts.py   # writes ui/src/generated/validity_rules.json
```

The CI contract-drift step verifies the committed artifacts stay byte-identical
to what the server serves.
